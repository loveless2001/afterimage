## Medium Priority Improvements

1. **Revisit does not reset or rebase the trail for the rewound run** — `js/afterimages-earlier-runs-trails-and-ghosts.js:40-57`, `js/endings-last-entry-secret-bench-and-screens.js:86-89`.
   `A.revisitEnding` calls `S.advance(G.state, { type: 'Revisit' })` directly (not through `A.finishRun`), so `A.trails.begin(run)` is never invoked. `Revisit` (in `game-rules-state-transitions-and-save-validation.js:71-77`) rewinds `state.run`/`state.budget` to the pre-ending values but leaves `state.player` untouched. Net effect: the trail recorded up to the moment the run finished (including its final "pause" mark from opening the log/bench) is kept, and any further play in the rewound run keeps appending to the *same* array rather than starting fresh. Since player position isn't reset either, this happens to look continuous today, but it's worth confirming this is the intended behavior (vs. "any run I re-enter should show a clean afterimage") — flagging as a design question, not a bug, since nothing crashes and the comment ("A run starting (again) begins a fresh trail") only documents the `EndRun`→next-run case, not Revisit.

2. **`draw.afterimage`'s shelf-occlusion check samples only one z-height** — `js/render-room-objects-and-characters.js:159-168` vs `agentGhost` at line 103-109, which checks `[20, 40, 60].some(z => hiddenAt(x, y, z))`. `afterimage(x, y, fade)` only checks `hiddenAt(x, y, 40)`. This is an intentional simplification (afterimages are just skipped when hidden, not drawn as a peek-through outline like the live player), but it means an afterimage standing just behind a shelf at a height where 40 reads as visible-but-20/60 would be hidden (or vice versa) won't be culled/shown consistently with how the live player is treated. Cosmetic only, low risk.

## Low Priority Suggestions

1. **`A.trails.record`'s "moved" flag is "attempted movement," not "actual movement"** — `js/input-movement-and-collision.js:57-66`. `length = Math.hypot(dx, dy)` is computed from input direction before collision is applied; if the player is fully blocked (held against a wall) `moved` is still `true`, so `add(here())` can push duplicate points at the same position every 0.25s while stuck. Doesn't break anything (duplicate points just interpolate to the same spot), but consumes cap budget faster than necessary and technically contradicts the module comment ("each run's path is sampled every 0.25s of play"). Not worth fixing unless the thinning cap becomes an issue in practice.

2. **`clock` accumulates real time while stationary, not just while moving** — same file/lines. Because `clock += dt` happens unconditionally and only resets when a sample is taken, standing idle for N seconds then moving again can trigger an immediate sample on the very next moving frame (clock already ≥ step). Harmless, just a minor timing quirk vs. the "every 0.25s of play" framing in the comment.

3. **Repeated thinning drift** — `js/afterimages-earlier-runs-trails-and-ghosts.js:27,37`. `thin()` re-filters on current array indices every time `add()` pushes past `cap` (400), rather than tracking a stable "every-other-original-point" invariant across repeated thin passes. Over a very long single run this could unevenly bias which older points survive, though pauses (`p[2]`) are always preserved regardless. The unit test only exercises a single `thin()` call on a 401-length array, not the cumulative effect of many incremental `add()`+`thin()` calls past the cap — acceptable for a cosmetic feature, just noting the test doesn't cover the repeated-application path.

## Positive Observations
- `trailPosition`/`thin`/`validTrail` are pure and Node-exportable (`module.exports` early-return pattern) — clean split, and I hand-traced all 7 assertions in the new test against the implementation; they check out exactly (glide, pause-hold, end-rest, loop-wrap).
- Ledger correctness verified end-to-end: `S.advance`'s `closeRun` pushes `{run, budget, spent, end, pin}` (`game-rules-state-transitions-and-save-validation.js:26-29`) and the ledger's `ended` map (`{left:'left', budget:'ran out', ending:'last entry'}`) matches `endReasons` (`['left','budget','ending']`) exactly. Cross-referencing the edited Playwright step's prior scripted actions (lamp cost 2 + note cost 1 = "spent 3", exactly 1 posted note, exit → "left"; run 2 spends all 6 budget with no notes → "—"/"ran out"), the regex `assert.match(rows[0], /^\s*01\s+10\s+3\s+1 note\s+left\s*$/)` and `rows[1]` line up with actual game state at that point in the script.
- Playwright `innerText` on a real `<table>`/`<tr>`/`<td>` does insert tab characters between cells and newlines between rows per the HTML rendered-text-collection algorithm (implemented consistently in Chromium/Firefox), so `.ledger tbody tr:not(.margin-row)` → `allInnerTexts()` with `\s+`-tolerant regexes is a sound approach, and `:not(.margin-row)` correctly excludes the `margin-row`/keeps `pencil`/`last-entry` rows out of the way for this specific test (no `last-entry` row exists yet at run 2/3, turnRun is 6).
- `A.el` was correctly hoisted from `notice-board-and-pinned-card-views.js` into the shared context module and both notice-board and ledger now share it — good DRY cleanup, no behavior change (verified identical implementation).
- Script load order in `index.html` (game-context at line 35 before both `run-log-ledger-page-view.js` line 40 and `afterimages-earlier-runs-trails-and-ghosts.js` line 52; the latter before `input-movement`, `render-room-objects`, `render-frame-loop`) is correct for every actual call site — all consumers of `A.trails`/`A.el` invoke them from inside functions/event handlers/rAF callbacks, never at top-level script-parse time, so earlier-loaded modules referencing them (e.g. `room-interactions-lamps-log-hall-exit.js` at line 41, before line 52) are safe.
- `dialog-modal-and-focus-trap.js`'s generalization from a single `wide` boolean toggle to `box.classList.remove('wide','book'); if (scene?.dataset.size) box.classList.add(scene.dataset.size)` is correct and covers both the wall (`dataset.size='wide'`, set in `notice-board-and-pinned-card-views.js:29`) and the ledger (`dataset.size='book'`, set in `run-log-ledger-page-view.js:24`) call sites; all 5 dialog callers that pass a scene were checked and remain consistent.
- Storage-failure handling is defensive throughout: module-load trail read and `persist()` both wrap the `localStorage` property access itself (not just method calls) in `try/catch`, matching the blocked-storage test's getter-throws simulation. Junk data under the trails key (non-object JSON, arrays, malformed per-run trails) degrades gracefully via `validTrail`'s `Array.isArray`/`Number.isFinite` guard rather than throwing.
